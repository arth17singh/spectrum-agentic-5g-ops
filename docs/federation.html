Federation Center

This is where five telecom operators train one shared network model together without showing each other their data. Each operator trains on its own private incidents. Only a small, masked model update leaves each operator, and a sealed aggregator combines the updates. The screen shows the training running, the privacy each operator has spent, what the server can and cannot see, and what happens when one operator turns hostile.

The screen in one minute

The one-sentence story: five operators improve one model together, nobody's raw data moves, the server only ever sees noise from any single operator, and a poisoned update gets thrown out.

The on-screen title is "Federated fine-tuning". The rail calls it "Federation Center". It belongs to the Learn plane, the first of the five planes in the lifecycle ribbon. The model it produces is promoted to the Proving Ground (Verify plane), which tests it before release.

  • Federated learning means the model travels to the data, not the data to the model. Each operator trains a copy locally and sends back only the change it made.
  • Fine-tuning with LoRA means the big base model (llama-3.2-1b-instruct) stays frozen. Each operator trains a small add-on (an "adapter", 21.6 MiB per update), so updates are small and cheap to move.
  • DP-SGD (differentially private training) limits how much any one record can change the model, and adds random noise, so the model cannot memorise a single incident. The privacy cost is counted as ε (epsilon). Lower is more private.
  • Secure aggregation means each update is scrambled with random masks. The masks cancel out only when all updates are added together, so the server learns the total and nothing else.
  • The enclave is a sealed compartment on the aggregation server. The masks can be removed only inside it, and only if it proves it runs the expected code. That lets it check individual updates for poisoning without anyone else seeing them.

See Concepts explained simply for longer explanations of these terms.

What happens in one training round

Every panel on this screen is a different view of the same repeating cycle. One round takes about 25 seconds at normal simulation speed. When it ends, the next round starts on its own.

  1. Pull1.0 s
  2. Local DP-SGD15 to 19 s
  3. Mask1.4 s
  4. Upload1.6 s
  5. Aggregate2.6 s, in enclave

Pull fetches the latest global adapter. Local DP-SGD runs 240 private training steps. Mask adds the secure-aggregation masks. Upload sends the 21.6 MiB masked update. Aggregate combines the updates inside the enclave, rejects outliers and signs the round.

The timings come from PHASE_TIME in backend/spectrum/engines/federation.py. Local training takes 16 s divided by each operator's speed: Op-C is fastest (about 14.8 s) and Op-D slowest (about 18.6 s). Aggregation waits for the slowest operator, so Op-D sets the pace of every round.

The three headline numbers are computed in the browser from the last round. Federation gain is (best alone − federated) ÷ best alone. The curves come from simple formulas in the simulator:

  • Federated loss = 0.56 + 0.09 × (σ − 1.1) + 1.72 × e−0.21 × round, plus a little noise. More privacy noise (higher σ) costs a little accuracy. If a poisoned update got in, that round's loss is 0.34 higher.

  • Each operator alone = its own floor + 1.5 × e−0.16 × round. The floors are 0.93 (A), 1.01 (B), 1.07 (C), 0.89 (D) and 1.16 (E). An operator alone can never get below its floor. That models the design idea: each operator sees only its own vendor dialect and fault mix, so it cannot generalise alone.

Privacy budget

panel privacy, file panels.tsx

What it is for

It tracks how much privacy each operator has spent so far against a hard limit. When an operator reaches the limit, it stops training automatically.

What it shows

  • Headline: "ε = 2.59", then "highest, Op-E, 86% of target 3". From 90% of the target a pill appears: amber "Near budget". At 100% it turns red: "Budget spent".
  • Chart: cumulative ε per operator, one line each with an end label. The X axis is rounds from r0. The Y axis runs from 0 to 4.0 at the default target (the code asks for 1.15 × target and rounds up to a tidy tick).
  • Red horizontal line "target ε 3": the budget.
  • During training, each line extends live to a fractional round. For example, halfway through round 13 is plotted at 12.5.
  • Footnote: "Operators with less data sample a larger share per step (higher q), so they spend budget faster. An operator that reaches its target leaves the federation automatically."

Pre-demo values: Op-A 0.98, Op-B 1.50, Op-C 1.95, Op-D 0.80, Op-E 2.59.

ε in plain words: a score for how much the trained model could reveal about any single record in an operator's data. 0 would be perfect privacy. Smaller is safer. δ = 1e-5 is the tiny probability that the guarantee does not hold.

Why the operators differ. The sampling rate q is the share of an operator's data used in one batch of 64. Op-E has only 7,000 samples, so q = 0.00914. Op-D has 22,600, so q = 0.00283. Spending grows with q², so Op-E spends about ten times faster than Op-D.

Why ε² is summed. Adding squared increments lets σ change mid-run and still compose sensibly. This is an approximation, and the code says so. In AWS mode the Opacus RDP accountant would replace it, which is what the source chip names.

The two thresholds:

  • At 90% of the target, the engine emits a warning fl.budget event once. You get an amber toast such as "Op-E at 90% of privacy budget (ε 2.70 of 3.0)".
  • At 100%, the operator stops training immediately, mid-round: its status becomes "budget exhausted", its step bar jumps to full, and a critical event says it "reached its ε budget and leaves the federation". Its update for that round is still aggregated, and from the next round it is left out.

DP-SGD internals

panel dp, file panels.tsx

What it is for

It opens up the privacy mechanism itself. It shows how big each training example's "push" on the model is, and how many pushes get cut down to a safe size.

What it shows

  • Ridgeline chart: one stacked curve per operator. Each curve shows how per-sample gradient sizes (L2 norms) are spread. The X axis runs from 0 to 3 × C (0.0 to 3.0).
  • White vertical marker "clip C = 1": the size limit.
  • Hatched area right of the marker: samples that get clipped.
  • Right-hand label per row: share clipped, such as "12.7% clipped" for Op-A and "17.4% clipped" for Op-E.
  • Settings column: Clip norm C 1.00, Noise multiplier σ 1.10, Noise std σ·C 1.10, Batch size 64, Sampling rate q 0.0028–0.0091 (lowest to highest operator), Steps per round 240, Learning rate 2e-4, LoRA r16, α32.
  • Footnote explaining clipping and noise.

DP-SGD in plain words. In normal training, every example nudges the model. DP-SGD measures each nudge. Any nudge bigger than C is shrunk to size C, so no single record can push hard. Then random noise of size σ·C is added to the batch total, so you cannot tell whether any one record was there.

How it works

Backend
Federation._emit_steps in engines/federation.py
Arrives by

Every second during the local training phase

Every second, for each operator that is training, the simulator draws 512 sample gradient sizes from a log-normal distribution and bins them into 40 bars between 0 and 3·C. Clipped share = the fraction above C.

  • The typical (median) size is C × (0.5 + 0.62 × e−0.13 × round) × (1 + 0.15 × (floor − 1)). Gradients shrink as training goes on, so clipping falls round by round.
  • Operators with a higher floor (Op-E, 1.16) have slightly bigger gradients, so they clip more.
  • The settings column reads the live config, so it changes when you apply new settings. Changing C also rescales the X axis and moves the marker.

Controls

None. It only displays data. Change C and σ in the Training settings drawer.

How to read it

Most of each curve should sit left of the white line. A small hatched tail (10 to 20%) is healthy: clipping bites only on unusual examples. A large hatched area would mean C is too small and training is being distorted.

How to demo it

This is real code doing real arithmetic:

  • Each operator's update is turned into whole numbers: multiply by 65,536 (2^16), then wrap around at 2^32.
  • For every pair of operators (5 operators give 10 pairs), the engine draws a random mask matrix. The first operator of the pair adds it, the second subtracts it.

  • When the host adds all five masked matrices, every mask meets its opposite and cancels. The engine compares the masked sum with the true sum and reports the largest difference. It is always exactly 0.
