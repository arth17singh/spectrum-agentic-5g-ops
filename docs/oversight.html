What this screen is for

The agent swarm on Swarm Tower fixes network problems on its own, but only small ones. A policy rule, P-003, says any radio change that touches more than 5% of the network's cells needs a human. When a plan breaks that rule, the swarm does not act. It files a request here and waits.

The one-sentence story: the agents propose, the policy stops them, a named person decides with all the evidence in front of them, and that decision is signed and provable later.

The life of one request

Every request on this page follows the same path through backend/spectrum/engines/oversight.py.

  1. Requestedapproval.requested
  2. Pending at L1A. Rivera, 2 min
  3. Pending at L2J. Okafor, 5 min
  4. Pending at L3M. Chen, 10 min
  5. Approved, rejected or expired
  • A request is created by Oversight.create. It gets the next id (APR-311 upward), a tier (high or critical), and a ledger record approval.requested.
  • It moves up one level when its SLA runs out (checked 10 times a second by Oversight.tick) or when someone presses Escalate.
  • It becomes approved when it has enough approvals: one for high, two different people for critical.
  • It becomes rejected as soon as anyone rejects it.
  • It becomes expired if the L3 SLA also runs out. Nothing is executed. The agents never act on silence. Expiry is silent in the current code: no event and no ledger record, so the console keeps showing the request as pending ("escalating…") until the page reloads, and the incident is never executed or closed. For APR-317 that takes 17 minutes, so it will not happen on stage.

Four-eyes, step by step

The second request in the demo, APR-318 "Release site-17 from quarantine", is critical. It needs two different people. It is filed by the sentinel agent during beat 10, after site-17 was fooled by a poisoned syslog line and quarantined. Its timer is 20 minutes at L1, so you can show it any time after beat 10.

  1. Fire beat 10 (→ from beat 9). It stays on Swarm Tower. About 3 seconds later the toast "APR-318 needs a human: Release site-17 from quarantine" appears.
  2. Click the toast's Review button, or press g o. The desk opens APR-318 (the newest pending request).
  3. With Signing as on A. Rivera, click "Approve (1 of 2)". The ceremony runs; the first slot turns green.
  4. Point out that the button now reads "A. Rivera already approved" and is disabled.
  5. For the second approval, have the teammate with the phone tap Approve (it signs as J. Okafor). Only in rehearsal, or if the phone fails, switch Signing as to J. Okafor and approve on the console; if you do that in front of judges, say plainly that in mock mode the name is chosen, not authenticated.
  6. The request turns Approved. The backend releases site-17 with a new key id and writes an identity.reissued record. Show the agent back to active on Swarm Tower.

Two details to know before a judge asks

  • The identity.reissued record is written as human:a.rivera whoever the two approvers were. The two approvals themselves are signed by the right people.
  • Site agents stay at autonomy L3 after the release (the top bar still reads "Autonomy L3 site"). Releasing the agent does not restore its peers' autonomy. A human restores it in Swarm Tower's Autonomy panel; that change is also a signed ledger record.

Getting phones connected

The phone does not talk to the internet. It talks straight to the presenter's laptop over the local network, so both must be able to see each other. Do this during setup, not on stage.

Steps

  1. Put the laptop and every approval phone on the same Wi-Fi. A phone hotspot that the laptop joins is the most reliable option at a venue.
  2. Start the console as usual (make dev, or make demo on demo day) and open it on the laptop at http://localhost:5173 (or http://localhost:8787 with make demo). Use the word localhost, not 127.0.0.1.
  3. Press d to open the Demo Director and click the Preflight tab.
  4. Check the URL under "Phone approvals". It must look like http://192.168.x.x:5173/m/approve (or :8787 with make demo): the laptop's address on the network, not 127.0.0.1.
  5. Scan the QR code with the phone's camera and open the link.
  6. On the phone, check the green Live dot and that Signing as reads J. Okafor, L2.
  7. On the laptop, wait up to 10 seconds: the row "Approval phones connected" turns to a green check with "1 other client(s)".
  8. If the phone cannot load the page, allow incoming connections when macOS asks: for Node with make dev (Vite serves port 5173) or for Python with make demo (port 8787). You can also check System Settings, Network, Firewall.

How the QR code and the check work

QR code
Built in the browser from the current address. If the console is open at localhost, the host is replaced with lan_ip from GET /api/director/preflight; otherwise the host you typed is kept. The port is the current port. The path is /m/approve. The backend finds lan_ip by asking the operating system which network interface it would use to reach the network, and falls back to 127.0.0.1 if there is none.
Phones connected
The same preflight call returns ws_clients, the number of open WebSocket connections. The row is green when there is more than one, and shows "ws_clients − 1 other client(s)". It refreshes every 10 seconds.
Dev mode path
Phone → laptop port 5173 (Vite is set to host: true so other devices can reach it) → Vite forwards /api and /ws to the backend on port 8787.
Demo-day path
make demo serves the built UI and the API from one process on port 8787, listening on all network interfaces.

What is real and what is simulated here

Real, even in mock mode

  • Ed25519 signatures on every human approval, rejection and manual escalation (one key per person); automatic escalations are signed with the oversight service key.
  • The hash-chained ledger records approval.requested, approval.decision and escalation.
  • The policy evaluator that blocks large radio changes until a human approves (P-003), outside the model.
  • The rules: four-eyes refusal of a repeat approver, SLA timers and escalation (expiry is enforced on the server but not announced or ledgered), no action on silence.
  • Live sync: each device keeps its own live WebSocket to the same backend.

Simulated, labelled as such

  • The three people and their roles; there is no sign-in.
  • The keys: generated from a fixed seed, named kms:…, not stored in AWS KMS.
  • The queue: in memory, instead of Step Functions task tokens.
  • Paging on escalation: no SNS or Incident Manager message is sent.
  • The twin pre-flight numbers, the incident, the dissent, the model opinions and the reason text on each request.

One honest sentence for judges

"The approval logic, the signatures and the ledger are real code running now; the people, the network and the paging are simulated, and in AWS mode they map to Cognito, Step Functions task tokens and SNS."
