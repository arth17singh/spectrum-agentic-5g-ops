How to prepare

Learn the first line for the concepts in your beats; skim the rest. Concepts per beat tells you which ones are yours. The cheat sheet at the end puts every one-liner on one page.

Two words used all over this page: a beat is one of the 14 numbered steps the Demo Director runs (see the Demo playbook). A reset (hold r for one second, or hold Reset in the Demo Director) rebuilds the same starting state every time: federated round 12 done and about 3,430 signed ledger records.

How the screens get their data

Almost every number in the console travels the same path. Knowing it helps you explain any panel.

  1. Engines tick10 times a second
  2. Event buseach engine emits typed events, e.g. fl.round
  3. One WebSocketa batch every 100 ms
  4. Browser storeone slice per engine
  5. Panel redrawsreads its slice

A WebSocket is one connection the server keeps open to push updates to the browser; REST commands are ordinary one-off web requests. When a console opens, it first loads the full current state with GET /api/snapshot, then applies events as they arrive. Buttons send REST commands such as POST /api/ledger/verify. Events that matter for the record are also written to the signed ledger, so the same action shows up on its own screen and on the Audit screen.

Two ideas explain what SPECTRUM trains: a small network model, and the cheap add-on that teaches it a new skill.

NLM (network large model)

Comes up in beats 2 13

A language model tuned for network operations work: reading alarms and KPIs, finding the root cause, and writing a plan of tool calls.

A family doctor who did an extra year of training in one specialty. Same brain, sharper at one job.

In SPECTRUM

The NLM is Llama 3.2 1B Instruct (llama-3.2-1b-instruct) plus a LoRA adapter that five operators train together. The task, as named in the code, is "network-ops instruction tuning (RCA + tool plans, vendor A/B dialects)".

Versions are nlm-v5, nlm-v6 (in production after a reset) and the next candidate, nlm-v7. Two size variants, nlm-0.5b and nlm-v7-3b, show how accuracy and cost change with size.

The 40 site agents run the NLM. The coordinator and the five domain agents run Bedrock models (Claude Sonnet, Claude Haiku, Nova Lite, Nova Pro).

On screen
Proving Ground, Scorecard, Pareto frontier and NLM scaling. Swarm Tower, Agent roster: the model column. Release, Rollout: which version serves. Observability, Tokens and cost compares it with Claude Sonnet.
Real or simulated
Simulated No model is loaded or called in mock mode. Benchmark numbers are illustrative, and an agent's "thinking" is a random delay and token count.
Deeper answer
"Why a small model?" Forty site agents on a frontier model would be slow and expensive. The modelled price for the NLM is $0.02 per million tokens in and out, against $3 in and $15 out for Claude Sonnet. That ratio drives the "Site-agent decisions, per 1K" figure on Observability, whose hint shows how many times more the same decisions would cost on Claude Sonnet (a little over 200 times with the simulated token mix). The cost-per-incident bars are fixed for earlier incidents and a formula for the live one; see Tokens and cost. The NLM price is an assumed amortised instance cost, not a list price.

LoRA fine-tuning, versus pretraining

Comes up in beat 2

LoRA teaches an existing model a new skill by training a small add-on, leaving the original untouched.

Pretraining is building the car. LoRA is fitting a tow bar: small, cheap, removable, and the car underneath is unchanged.

In SPECTRUM

The add-on is called an adapter. Pretraining, by contrast, builds a model from scratch on huge amounts of data.

LoRA rank 16, alpha 32 (rank sets the adapter's size; alpha sets how strongly it counts), on the four attention projections, the layers that decide which words the model pays attention to (q_proj, k_proj, v_proj, o_proj). The adapter is about 21.6 MiB (22,675,456 bytes, stored as fp16, that is 16-bit numbers). It is the only thing that travels between an operator and the aggregator.

Training plan: 30 rounds, 240 local steps per round, batch size 64, learning rate 2e-4, one local epoch.

On screen
Federation Center, Run strip: "Adapter: LoRA r16, α32", with q_proj, k_proj, v_proj, o_proj underneath. DP-SGD internals: the LoRA row ("r16, α32"). Data sovereignty: "Adapter updates moved".
Real or simulated
Simulated The settings are realistic configuration, but no adapter is trained in mock mode. In AWS mode each operator would run Flower and Opacus in its own ECS task.
Deeper answer
"Is this pretraining?" No. It is federated fine-tuning of a 1B model; pretraining is out of scope. A small adapter keeps each upload to about 21.6 MiB per operator per round, which makes federation practical, and fewer trainable parameters make differential privacy cheaper.

Five embassies share a summary memo; the files never leave each building.

DP-SGD (differentially private training)

Comes up in beat 2

Training that caps each record's influence and adds random noise, so the model can't memorise any single record.

A survey where every answer is blurred a little. The averages stay accurate, but nobody's own answer can be read back.

In SPECTRUM

Record-level DP-SGD on the LoRA parameters. At each step: compute each sample's gradient (its push on the model), clip it to length C (default 1.0), add Gaussian noise with standard deviation σ·C (σ default 1.1) to the batch sum, then take the step. Batch 64, 240 steps per round.

Changing σ or C in Training settings writes an fl.config ledger record and adds a marker to the charts.

On screen
Federation Center, DP-SGD internals; Privacy budget; "Privacy σ 1.1, C 1" in the Run strip. Beat 2 spotlights the privacy panel.
Real or simulated
Simulated No gradients exist in mock mode. AWS mode would use Opacus per-sample gradients.
Deeper answer
"Record-level or client-level privacy?" Record-level: it protects individual incidents and subscribers inside each operator's data. Protecting a whole operator (client-level DP) needs many more participants than five. Secure aggregation is what protects each operator's update from the server. As SPECTRUM.md puts it: we built the mechanism, not a production privacy guarantee.

Clipping and the clip norm C

Comes up in beat 2

Capping the size of each sample's gradient, so no single record can push the model hard.

However loudly one person shouts, their vote still counts once.

In SPECTRUM

C defaults to 1.0 (slider from 0.1 to 5). About once a second the server sends a picture of each operator's gradient lengths and the share above C. The typical gradient starts larger than C and shrinks as rounds pass, so the clipped share falls during training.

Deeper detail

The fl.gradhist event carries, per operator, a histogram of 512 simulated gradient lengths in 40 bins from 0 to 3·C, plus the share above C.

On screen
Federation Center, DP-SGD internals: one ridgeline per operator (a stacked row of curves showing how gradient lengths are spread), the vertical "clip C = 1" line, the hatched area to its right, and "x% clipped" per operator. The slider is in the Training settings drawer.
Real or simulated
Simulated The gradient lengths are random draws (from a log-normal distribution, a skewed bell curve with a long tail of large values); nothing is really clipped in mock mode.
Deeper answer
"How do you pick C?" Too small and most samples are cut, losing signal. Too large and you need more noise for the same privacy. A common choice is near the typical gradient length, which is what the ridgeline lets you see.

Noise multiplier σ (sigma)

Comes up in beat 2

The dial that sets how much noise DP-SGD adds, relative to the clip norm.

The amount of static on a phone line: more static, more privacy, harder to hear.

In SPECTRUM

σ defaults to 1.1 (slider from 0.3 to 3). Noise standard deviation is σ·C. In the simulator a higher σ spends privacy more slowly but makes the model a little worse.

As you move the slider, the drawer shows each operator's projected ε at the end of the run, with red bars for operators that would run out early. The slider changes nothing until you press "Apply changes", which writes an fl.config ledger record. (The Participation toggles in the same drawer act immediately.)

Deeper detail

The ε increment scales with 1/σ², and the loss floor rises by 0.09 for every 1.0 of σ above 1.1. The projection comes from GET /api/fl/projected_eps.

On screen
Federation Center, Training settings drawer ("Noise multiplier σ", "Projected ε at round N with these settings"); DP-SGD internals ("Noise multiplier σ", "Noise std σ·C").
Real or simulated
Simulated The trade-off is modelled. The projection uses the same accountant formula as the live chart, so the two agree.
Deeper answer
"What is the privacy versus accuracy trade-off?" More noise means lower ε but a worse model. Showing the projection before applying a change lets an operator check its budget lasts the whole run.

Privacy budget ε and δ, and the accountant

Comes up in beat 2

ε (epsilon) counts how much privacy has been spent; lower is more private, and each operator has a cap.

A prepaid privacy card. Every training step spends a little; when the card is empty, you stop.

In SPECTRUM

δ (delta) is the tiny chance the guarantee does not hold. The accountant is the code that keeps the running total of ε.

Each operator has a target ε of 3.0 with δ = 1e-5. Smaller operators spend their budget faster, because each training step samples a bigger share of their data.

Deeper detail

The sampling rate q is batch size divided by data size: 64 ÷ 18,400 ≈ 0.0035 for Op-A, 64 ÷ 7,000 ≈ 0.0091 for Op-E. The mock accountant adds up squared increments, (1.71 × q ÷ σ)² × steps × ln(1/δ), and ε is the square root of the total. Adding squares is what lets σ change mid-run and still add up sensibly.

At 90% of the target the server emits a warning. At the target the operator's status becomes budget_exhausted and it leaves the federation. With default settings Op-E is at ε ≈ 2.59 after round 12, passes 90% early in round 14 and runs out during round 17.

On screen
Federation Center, Privacy budget ("cumulative ε per operator, δ = 1e-5", red target line, "Near budget" or "Budget spent" pill); Client fleet status. Ribbon: Learn segment "ε max x.xx of 3". Beat 2 spotlights this panel.
Real or simulated
Simulated The README says so directly: the accountant is an approximation that composes correctly when σ changes. AWS mode would use the Opacus RDP accountant, which is what the AI-BOM names.
Deeper answer
"What is your real ε?" In this demo ε comes from the approximate accountant, so call it a simulated number. A real run would report the Opacus RDP accountant's ε at δ = 1e-5, per operator, record level.
Watch out
If training runs past round 16, Op-E leaves the federation. This is expected. Say: "its privacy budget is spent, so it stops".

Secure aggregation with pairwise masks

Comes up in beat 3

A way of adding up everyone's updates so the server learns only the total, never any single operator's update.

Five friends want their average salary without telling anyone their own. Each pair agrees a random number; one adds it, the other subtracts it. Every slip of paper looks like nonsense, but the random numbers cancel in the total.

In SPECTRUM

Every pair of operators shares a random mask: a 16 × 16 grid of whole numbers between 0 and 2^32. For a pair, the first operator adds the mask and the second subtracts it. Updates are first turned into whole numbers (multiplied by 2^16), and all sums wrap around at 2^32, so the masks cancel exactly, with no rounding error.

n operators share n(n−1)/2 masks, one per pair: 10 for five, 6 for four (the panel shows the live count). After each round the server reports the largest difference between the masked sum and the true sum, which is 0. The panel labels dropout recovery as "Shamir t=3 of 5" (the mask secret split so that any 3 of the 5 operators could finish a round if others drop out).

On screen
Federation Center, Secure aggregation ("what the untrusted host sees"): five noise-like heatmaps, Σ, the aggregate heatmap, and the readouts "max |Σ masked − Σ true|", "pairwise masks", "dropout recovery", "arithmetic". "Show true updates" (on by default through the demo.privileged_view flag) swaps in the unmasked grids, and the button then reads "Privileged view (demo)". Click it again to go back to the masked view before you move on. Beat 3 only opens and spotlights this panel in the masked view; click "Show true updates" yourself if you want the contrast.
Real or simulated
Real The masking maths runs for real every round, on a 16 × 16 demonstration grid per operator rather than on the 21.6 MiB adapter. Shamir dropout recovery is a label only: "Drop" marks an operator as dropped and it stops training. A drop takes effect from the next round; an operator dropped mid-round is still in that round's masked sum.
Deeper answer
"If the server can't see updates, how do you catch a poisoned one?" With masking alone you can't, and we say so. That is why the default mode is masking plus an attested enclave, which is allowed to see individual updates and run robust aggregation. See poisoning.

Nitro Enclave, attestation and KMS

Comes up in beats 3 4

A sealed server that proves which code it runs, so a key is released only to that exact code.

A sealed counting room. A certified seal on the door proves nobody changed the room, and the key to the ballot box is handed over only if the seal matches.

In SPECTRUM

An enclave is a sealed compute box that even its owner can't log in to. Attestation is its signed proof of exactly which code it runs. KMS (AWS Key Management Service) hands over a key only to a box with the right proof.

The aggregator image is spectrum-aggregator-v0.4.2.eif, measured as PCR0 (image), PCR1 (kernel) and PCR2 (application); a PCR is a hash of one part of what the enclave booted. Operators release their mask seeds only to a KMS key whose policy has the condition kms:RecipientAttestation:PCR0. Chain of trust: AWS Nitro Enclaves Root-G1, enclave certificate, attestation document, KMS key policy, mask seeds released.

Three secure-aggregation modes: Masking, Masking + enclave (the default) and CKKS (HE). In enclave mode each round record carries attestation_pcr0: "verified".

On screen
Federation Center, Enclave attestation (pill "Attested" or "Enclave mode off", and a "Switch to enclave mode" button when it is off). Trust Center, Enclave attestation chain. Audit, Provenance: the "Nitro Enclave attestation" node.
Real or simulated
Simulated The PCR values are hashes of fixed strings and no enclave runs in mock mode. The mode itself does change behaviour: only in enclave mode are poisoned updates rejected.
Deeper answer
"Can your own team see the updates?" That is what the key-policy condition is for: the key works only for the measured image. As the panel says, change one byte of the aggregator image and the key stops working, for us too. In this demo the attestation values are simulated; the design is what we are showing.

Homomorphic encryption (CKKS)

Not in a scripted beat; for judge questions

Encryption that lets a server add numbers while they stay encrypted. CKKS is a scheme built for approximate arithmetic on real numbers, like model weights.

Totting up sealed envelopes of cash by weighing them, without opening any.

In SPECTRUM

A stretch micro-demo on a 4,096-weight slice. Settings: polynomial modulus degree 8,192, coefficient modulus [60, 40, 40, 60] bits, scale 2^40, 128-bit security. The ciphertext is 512 KiB for a 16 KiB plaintext slice (32 times bigger).

The noise budget starts at 97 bits, drops 2 bits per operator added, and ends at 57 bits after rescaling. Decrypt error is around 3 × 10⁻⁷. Choosing CKKS (HE) mode makes the Secure phase 1.6 times longer.

On screen
Federation Center, Homomorphic encryption ("stretch: CKKS micro-demo on a 4,096-weight slice"): settings, ciphertext expansion bars, noise budget bars, and encrypt, aggregate and decrypt times.
Real or simulated
Simulated Every number on the panel is generated (its source chip says "Simulated CKKS stats"). AWS mode names TenSEAL or OpenFHE (open-source homomorphic encryption libraries) on ECS.
Deeper answer
"Why not encrypt everything this way?" Cost: messages 32 times bigger and a noise budget that limits how many operations you can do. And like pure masking, a server adding ciphertexts is blind, so in CKKS mode a poisoned update is accepted, not rejected.

Poisoning and robust aggregation

Comes up in beat 4

Poisoning is sending a deliberately bad update to damage the shared model; robust aggregation leaves such outliers out.

In a judged contest the wildest score is thrown out, so one biased judge can't swing the result.

In SPECTRUM

Beat 4, or the "Poison" button in Client fleet, makes Op-E's next update a flipped, nine-times-amplified copy. Its size (L2 norm, the overall length of the update) is set to 14.2 times the median, a fixed demo value.

At aggregation the cut-off is median + 4·MAD. MAD (median absolute deviation) is the typical distance from the median, with a floor of 0.04. An update above the cut-off is rejected only if the mode is Masking + enclave and the strategy is not FedAvg. Otherwise it is aggregated, and the global loss rises by 0.34 and accuracy falls by 9 points. The decision goes into the round record and an fl.poison event.

On screen
Federation Center, Client update norms (dots per round, the dashed "threshold median + 4·MAD" line, a red × for the outlier, and an explanation box); Client fleet; Training settings drawer: Strategy (FedAvg, Trimmed mean, Krum, Norm-bounded) and Secure aggregation mode.
Real or simulated
Partly real The outlier test is real code but runs on simulated sizes. Trimmed mean, Krum and Norm-bounded behave the same here: any strategy except FedAvg rejects the outlier in enclave mode.
Deeper answer
"Doesn't secure aggregation stop you seeing this?" Yes, and we show that trade-off on purpose: in Masking or CKKS mode the server is blind, so the poisoned update gets in. Enclave mode closes the gap because the attested enclave is allowed to see individual updates.
Watch out
Before beat 4, open the Training settings drawer and check that the mode is "Masking + enclave" and the strategy is not FedAvg. If someone changed either earlier, the poisoned update is accepted, loss jumps by 0.34, and "the enclave rejects it" fails on stage. If so, reset before you start (hold r).

Checkpoint

Comes up in beat 5

A saved snapshot of the model at one point in training, so you can test it, ship it, or go back to it.

A save point in a video game.

In SPECTRUM

The aggregator saves one automatically every 2 rounds, and you can save one by hand. Each has an id such as ckpt-r12, the round, validation loss, accuracy, the highest ε of any operator, the adapter's SHA-256 hash and an S3 path ending in adapter.safetensors.

Hash chain

Comes up in beat 12

A list of records where each one includes the fingerprint of the record before it, so history can't be changed quietly.

A numbered logbook where each page starts by copying a stamp from the page before.

In SPECTRUM

Each record's hash covers its own contents plus the previous record's hash, so changing an old record breaks the link to every later one.

Deeper detail

hashn = SHA-256( canonical(bodyn) + hashn−1 ). The body is the record's seq, ts, type, actor, plane, payload and key_id. Record 1 links to a "genesis" value of 64 zeros. Each record also stores prev_hash, its hash, alg: Ed25519 and its signature.

A reset rebuilds about 3,430 records. Every engine writes to it; record types include fl.round, fl.checkpoint, eval.gate, aibom.signed, release.stage, tool.call, a2a.message, approval.decision, escalation, identity.revoked, autonomy.change, incident.resolved, loop.enqueue and dossier.generated.

"Verify chain" (POST /api/ledger/verify) walks every record from the start and checks three things: the hash matches, the link matches, the signature is valid. It stops at the first record that fails.

On screen
Audit, Hash chain, Records, Record #N ("Canonical body (sorted keys, no whitespace)", "hash = SHA-256(body ‖ prev_hash)", "SHA-256 recomputed in this browser"). Ribbon: Prove segment "Ledger #N".
Real or simulated
Real Kept in memory in mock mode (AWS mode: DynamoDB).
Deeper answer
"Couldn't an attacker recompute all the hashes?" They could recompute the hashes, but not the signatures, because they don't hold the keys. And they can't change the Merkle roots already locked in S3 Object Lock. That is why there are three layers.

Comes up in beat 12

"Why every 32 records and not every record?" Batching keeps the storage writes cheap while still fixing each record in place soon after it is written. The newest records, after the last anchor, are signed but not yet anchored.

Closing the loop

Comes up in beat 14

A resolved incident becomes new private training data for the next federated round, so the model keeps improving from real outages.

A hospital adds every hard case to its training for next year's doctors, without sending patient files to other hospitals.

In SPECTRUM

Beat 14 writes a loop.enqueue ledger record: the incident id, the destination "op-a private incident store", the consent basis "operator policy OP-A-7", and the next round number. The event reads "… queued as private training data at Op-A for round N".

On screen

Real or simulated
Simulated No data is actually moved or trained on. The signed record is real.
Deeper answer
"Doesn't that share incident data?" No. The incident goes into the operator's own private store, where only that operator's local training reads it. Only the adapter update leaves, as in every round.
Watch out
The beat 14 presenter note says "private training data at each operator". The signed record names one operator, Op-A, where the incident happened. Say "at the operator where it happened".
