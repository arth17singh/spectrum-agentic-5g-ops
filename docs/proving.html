Verify plane

Proving Ground

The Proving Ground is the exam a newly trained model must pass before it may serve any traffic. A checkpoint from federated training is scored on accuracy, safety, speed and price, then on private test sets held by each of the five operators. Its bill of materials is signed, and a fixed policy (the deploy gate) decides whether it may move on to a shadow release. Every decision is written to the signed ledger.

Route /proving Go to it with g then p Appears in demo beats 5

What this screen is for

One sentence story: "The new model has to earn its way in." Federated training on the Federation Center produces a checkpoint (a saved copy of the trained adapter). On this screen that checkpoint becomes a candidate model, for example nlm-v7. It runs through nine automated checks and is compared with the model now in production (nlm-v6) and with five third-party baselines. If it clears the four gate thresholds, it goes straight to a shadow deployment on the Release screen.

The page is tagged T1 (Track 1: NLM training, scaling and production readiness). It answers the Track 1 question directly: price, performance, accuracy and safety, measured the same way every time, with a deploy decision you can audit.

Real vs simulated on this page

The scores are illustrative. Every accuracy, safety, latency, throughput and price number comes from a fixed model table in backend/spectrum/engines/proving.py, or for a new candidate from a fixed formula in the same file, not from running real benchmarks. They are not real results for the named products (Llama, Amazon Nova, Claude). Hover any panel's source chip: the score panels say "Illustrative mock results", the pipeline says "Simulated state machine", the gate "Cedar mirror" and the AI-BOM "Ed25519 keyring" (see card 16). What is real: the Ed25519 signatures on the AI-BOM and on each operator's score, the SHA-256 digest of the AI-BOM, the gate's threshold logic, and the signed ledger records the run writes.

What it is for

It shows the evaluation as an assembly line of nine checks. The audience can see that a model is tested step by step, automatically, and in a fixed order. It mirrors an AWS Step Functions state machine (an AWS service that runs a workflow as a series of steps).

  • Footer (once a run exists): "Execution" with the Step Functions ARN, "Started" with the clock time, and "Recent runs": up to four chips, newest first, each with the run id, the model and a green check (passed) or red cross (blocked).

How it works

Backend

Each tick adds the elapsed time to the current stage. Progress is elapsed time divided by the stage's planned time. At 100% the stage is marked passed, the next stage starts, and an eval.stage event goes out. The detail counters are simply progress × 1,840, × 64 or × 5. The whole run takes about 18 seconds at normal speed.

Three stages do real work when they finish. Federated eval creates and signs the five operator scores (card 12). Sign AI-BOM builds and signs the bill of materials (card 15). Gate applies the four thresholds (card 14), sets the run to passed or blocked, appends the eval.gate ledger record and, on a pass, tells Release to start a shadow deployment.

Controls

None. It only displays data. Runs are started by cards 3 and 4, the command palette, or beat 5.

How to read it

Read left to right. Green bars are done. The coloured card is where the run is now. The header pill gives the final verdict: Gate passed or Blocked.

How to demo it

  1. Press 5. The page opens and the run starts.
  2. Follow the coloured card with your hand as it moves. Call out Accuracy, Safety red-team and Federated eval as their counters run.
  3. When the pill turns to "Gate passed", move to the scorecard.

What to say

"Nine automated checks, in a fixed order, every time: accuracy on 1,840 network tasks, 64 attacks, latency, price, then each operator scores it privately. Then we sign a bill of materials and apply the gate."

Judge question it answers

"How do you get a model safely into production?" Through a repeatable pipeline with a signed gate decision at the end (T1).

Real or simulated

Simulated The stages are timers, not real jobs, and the execution ARN is invented (account 111122223333). In AWS mode this maps to a Step Functions state machine.

Watch out

Stage 9, "Gate", shows a green check even when the gate blocks the model: the check means the step ran, not that the model passed. Read the verdict from the header pill. Also, stages never fail in this mock, so a red cross icon will not appear on a stage card.

Pareto frontier

panel pareto, panels.tsx Pareto

What it is for

It shows cost against accuracy for all nine or ten models in one picture, and draws a line through the models that are the best deal. "Pareto frontier" means the set of models that no other model beats on both cost and accuracy at once.

What it shows

  • X axis: "$ per 1K tasks", on a log scale (equal distances mean equal ratios; ticks at $0.02, $0.05, $0.10 … $10.0), so cheap and expensive models fit on one chart.
  • Y axis: "accuracy" in %, from about 50% to 90%.
  • Dots: one per model. Amber means the picked candidate (with a ring), blue means production, green means our other federated models, grey means baselines.
  • Labels: only on frontier models and the candidate. Before the demo: nlm-0.5b, nlm-v6, nlm-v7-3b and claude-sonnet.
  • Line: joins the frontier models from cheapest to dearest.
  • Legend and note below: the legend reads "Candidate", "Production", "Other federated NLMs" and "Baselines" (the four dot colours). The note reads "The line joins models no other model beats on both cost and accuracy. Up and to the left is better."

How it works

Store slice
proving.models (usd_per_1k, accuracy)
Computed in
paretoIds() in features/proving/model.ts, in the browser
Changes when

The frontier calculation: sort the models by price, cheapest first (ties broken by higher accuracy). Walk the list and keep a model only if it is more accurate than every cheaper model kept so far. With the demo data that gives nlm-0.5b ($0.02, 79.2%), nlm-v6 ($0.04, 84.3%), nlm-v7-3b ($0.11, 89.6%) and claude-sonnet ($12.0, 90.4%). Once nlm-v7 ($0.04, 87.3%) exists, it replaces nlm-v6 on the frontier.

Signing: the server builds the document, writes it as canonical JSON (keys in a fixed order, no extra spaces, so the same content always gives the same bytes) and takes its SHA-256 digest. A digest is a fingerprint: change one character and it changes completely. It then signs the digest with an Ed25519 private key. Ed25519 is a standard digital-signature scheme: only the private key can sign, and anyone with the public key can check.

Verifying: GET /api/eval/aibom/<model>/verify takes the stored document and removes the digest, signature and time. It recomputes the canonical digest and compares it with the stored one, then checks the signature with the signer key. It returns digest_matches and signature_valid, which become the two lines in the result box.
