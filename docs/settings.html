Settings, feature flags and presenter view

Two pages that judges rarely see but that decide whether the demo goes smoothly. The Settings screen turns parts of the console on or off, shows where every panel gets its data, and controls the simulation clock and the display. The presenter view is a separate full-screen page for a second laptop: it shows the script for each beat, a 7-minute timer and a preflight check, and it drives the projector console from there.

Routes /settings and /presenter Go to Settings with g then , (the presenter view has no hotkey: type the URL) Appears in no demo beat

What these two pages are for

The other screens show SPECTRUM doing its job. These two show how the console itself is put together and how you run the demo with it.

  • Settings (/settings) belongs to no plane. It is a control room for the console: 36 feature flags, the list of registered screens, where the data comes from (mock or AWS), the simulation speed, and display options.
  • Presenter view (/presenter) is a "bare" page: it does not draw the console frame (no top bar, ribbon or rail). It is meant for a second laptop that faces the presenter, not the audience.

A feature flag is an on/off switch in the code. When a flag is off, the part of the screen it guards is not drawn at all, and nothing else breaks. That is how the team can hide a half-finished panel or the demo-only buttons without changing code.

The one-sentence story

"Every screen, the optional panels and the attack, tamper and poison controls sit behind a flag, so we can switch them off live in a browser, or for everyone through remote config after a reload, and the console tells you which source decided each one."

When these pages appear in the demo

Neither page is the route of any of the 14 beats in engine.py. Use them like this:

How a flag's value is decided

inside panel flags, upper left

What it is for

Explains, with live counts, the four places a flag's value can come from, and that the last one wins. It answers "why is this flag on?" before anyone has to ask.

What it shows

A label, "How a flag's value is decided (last one wins)", then four boxes in order, each with a number, a name and a live count. Under them, one line of rules.

BoxCount in the captureWhat the count means
1 Code default"36 defined in code"Every flag has a default in core/flags.tsx. All 36 defaults are on.
2 Remote config"2 from /api/config/flags"Flags whose value came from the backend file. Today flags.json sets fl.he and demo.tamper to true, so the count is 2.
3 This browser"0 overridden here"Flags you toggled in this browser (saved in localStorage).
4 URL"0 via ?ff="Flags set by the ?ff= part of the address this tab was opened with.

The rule line reads: "A flag is only effective when every flag it depends on is also on. Turning off a screen hides its route, nav item, palette commands and panels together."

How it works

Function
rawValue(id) in core/flags.tsx returns a value and its source.
Counts
Computed in FlagsPanel by counting rows whose source is remote, local or URL.
Changes when
You toggle a flag, apply a preset, open a URL with ?ff=, or reload after editing flags.json.
  1. 1 Code defaultFLAGS[].default
  2. 2 Remote config/api/config/flags
  3. 3 This browserspectrum.flags
  4. 4 URL?ff=a:on,b:off
  5. Dependency checkeffective value

In code, rawValue checks the sources from the strongest down: if the URL set the flag, that wins; otherwise this browser; otherwise remote; otherwise the code default. Then isOn walks the dependsOn list: the flag counts as on only if its own value is on and every flag it depends on is effectively on too (it follows chains, for example demo.privileged_view needs fl.secagg_viz, which needs screen.federation). The full rules, with examples, are in How flag resolution works.

Controls

None. It only displays data.

How to read it

Read it left to right; anything further right overrides anything to its left. For the demo, boxes 3 and 4 should both read 0, so nobody's local experiments leak onto the projector.

What to say

"A flag starts from its code default, remote config can override it, an operator can override it in their browser, and a URL can override everything for one session."

Judge question it answers

"Can you roll a feature out to some users and not others?" Per device or per link, yes: an operator can override a flag in their browser, and a URL can override it for one session. Targeting by user or percentage would come from AWS AppConfig, which this build maps to but does not call yet. Track 1, production readiness.

Real or simulated

Real The counts are computed from the live flag store; the remote layer is the real backend file.

Watch out

The remote count of 2 does not change anything you can see: both remote values are true, the same as the defaults. Do not claim remote config is "turning something on".

  2. POST /api/sim{"speed": 2} or {"paused": true}
  3. Clock updatedspeed limited to 0.25–10
  4. sim.clock event"simulation running at 2.0×"
  5. Every console updatestop bar shows "2×" or "Paused"

Each engine tick advances simulated time by real elapsed time multiplied by the speed; when paused it advances by zero, so charts, training and the twin all freeze together. The change goes through the server, so the projector, the presenter laptop and phones all see the same clock. The sim.clock event appears in the live stream as a notice. It does not write a ledger record.

How flag resolution works

Each flag has up to four values, one per source. The strongest source that has a value wins. Then the dependency check decides whether the flag is effectively on.

OrderSourceWhere it livesWhen it is readLasts
1Code defaultFLAGS[].default in frontend/src/core/flags.tsxBuild timeUntil the code changes
2Remote configGET /api/config/flags, which returns backend/spectrum/flags.json. Keys starting with _ (such as _comment) are ignored.Once, when the console loads in that tabFor everyone who loads the console after the file changes
3This browserlocalStorage["spectrum.flags"], written by switches and presetsOn load and on every changeIn this browser until cleared
4URL?ff=key:on,key:off in the addressOnce, when the page loadsFor this tab until you reload without it
  • URL syntax. Comma-separated key:value pairs. The value counts as off only if it is off, 0 or false; anything else, or no value at all (?ff=fl.he), means on.
  • The URL is read once. It is parsed when the page loads and kept in memory, so it stays in force when you move to other screens even though the address bar no longer shows it. It is never saved: a reload without ?ff= drops it. A URL-set flag has its switch locked in the table.
  • Remote is read once per page load. The backend reads flags.json on every request, so no backend restart is needed, but each browser must reload to pick up a change.
  • Dependencies. A flag is effectively on only if its own value is on and every flag in its dependsOn list is effectively on, following chains.

Setting up the second laptop

  1. On the laptop that runs the backend and drives the projector, start the console (make dev, or make demo for the single-process build on :8787) and open it on the projector.
  2. Find that laptop's network address. The Demo Director's Preflight tab shows it in the phone QR link.
  3. On the second laptop, open http://<laptop-LAN-IP>:5173/presenter (or :8787/presenter after make demo). Vite is configured with host: true, so other devices on the same network can reach it.
  4. Check that all five preflight rows are green, then click Restart timer.
  5. On the projector, press d to hide the Demo Director, or load it with ?ff=demo.director:off. Check spotlight is on there (s).
  6. Plug the clicker into the second laptop and press PageDown to start.

Each browser has its own settings

Flags, theme, density, spotlight and the timer are stored per browser. Set the projector's look on the projector machine. Simulation speed, pause and the current beat are shared, because they live on the server.

60-second walkthrough

If a judge asks "walk me through this page" on Settings:

"This is how the console is built and run. Every screen, the optional and beta panels, and the attack, tamper and poison controls are behind one of 36 feature flags. A flag's value comes from code, then remote config, then this browser, then the URL, and this column shows which one won. Dependencies are explicit: switch off the federation screen and its panels go with it. These presets give us the judge demo, a minimal core, or an operator view without the attack, tamper and Director controls. Below, every screen is a module with a small manifest, which is how we built them in parallel. And here we are honest about data: we run on the mock engine, and these seams are where DynamoDB, S3 Object Lock, KMS, Verified Permissions and the other AWS services plug in. The simulation is seeded, so every run is repeatable."

"The director state lives on the server. From this laptop I fire each beat; the server runs it and every screen follows. I see the line to say, the next beat, a timer against our seven minutes, and a live preflight check."
