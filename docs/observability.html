What this screen is for

Every other screen shows one plane. This one cuts across all five. It answers the questions an operations team asks after something happens: what did the system do, how long did each step take, what did it cost, and is anything over its limit?

The one-sentence story for this screen, taken from the beat 13 presenter note:

"Every agent step is traced. The fine-tuned model runs 40 site agents for a fraction of a frontier model's cost."

It belongs to no single plane. In the code its rail entry has plane all, and its page header carries two track tags: Obs (observability) and T1 (Track 1: NLM training, scaling and production readiness). The cost panel is the Track 1 price-performance argument. The trace and agent health panels support Track 3 (traceability of a multi-agent swarm).

Real vs simulated on this screen

Treat every number on this screen as simulated or modelled. The metrics, latencies, token counts, GPU readings and SLO figures all come from the mock observability engine (backend/spectrum/engines/observability.py). Prices are assumed list prices. The README lists token prices as "modelled list-price assumptions".

Two things are real. The trace's shape follows real code paths: inside an incident or attack trace, a span is written each time an agent sends a signed message or calls a tool, and for the model calls of the coordinator and domain agents (and of site-17 in the attack). Site agents' model calls during the incident are not traced. Routine background work is not traced. And the policy decision inside a trace (permit or deny) is the real decision from the policy evaluator.

The source chips name the AWS service each panel maps to (CloudWatch, X-Ray, AgentCore). In this build the observability engine never calls the AWS adapter, so the numbers come from the engine in either mode.

Words used on this page

Each term in one plain sentence, so you can explain it without notes.

Trace

The full record of one piece of work (here, one incident or one attack) broken into timed steps.

Like a parcel's tracking history: every hand-off, with a time stamp.

Where you see it: Trace

Span

One timed step inside a trace, such as one model call, one message or one tool call. It has a start, an end, a parent and some attributes.

One line in the tracking history.

Where you see it: Trace waterfall

OpenTelemetry (OTel)

An open standard for recording traces, metrics and logs so any tool can read them. ADOT is AWS's distribution of it, and X-Ray is AWS's trace viewer.

A shared shipping-label format that every courier understands.

Where you see it: the Trace subtitle and the "AWS X-Ray (via ADOT)" chip.

GenAI semantic conventions

The agreed OTel attribute names for model calls, such as gen_ai.request.model and gen_ai.usage.input_tokens.

Standard column names on an invoice, so any accountant can read it.

Where you see it: Span detail

Golden signals

Four health numbers for any service: rate (how much work), errors, duration (how long), and saturation (how full).

Pulse, temperature, blood pressure and oxygen for a service.

Where you see it: Golden signals

p95

The 95th percentile: 95 of every 100 requests were at least this fast. It shows the slow tail that an average hides.

How long the slowest few customers in the queue waited.

Where you see it: Golden signals, Latency, Model endpoints

SLO, error budget, burn rate

An SLO (service level objective) is a reliability target, for example "99.5% of tool calls succeed". The error budget is the 0.5% you are allowed to miss. Burn rate is how fast you are using that budget: 1× uses it up in exactly the 30-day window.

A monthly data allowance and how fast you are using it.

Where you see it: Service level objectives

Modelled cost

Cost computed as tokens counted times an assumed list price per million tokens. No bill was paid.

A quote from a price list, not a receipt.

Where you see it: Tokens and cost, Cost per incident

A trace id is the first 32 hex characters of a SHA-256 hash of the title and the time. The engine keeps the last 30 traces and drops spans of older ones. The obs.trace and obs.span events are sent with record=False, which keeps them out of the server's event history, so the snapshot never replays them as stream events. They are telemetry, not evidence: nothing calls the ledger for a span, so spans are never signed ledger records. They are also on the store's "noisy" list, so they never show in the live stream or the log search.

Which trace is shown: the one you picked, if it still exists. Otherwise the newest trace tied to an incident, otherwise the newest trace. Beat 13 forces INC-2041 (see What beat 13 actually does). That is why the attack trace from beat 10 does not take over the panel, even though it is newer: it has no incident id.

All summary numbers are computed in the browser from the span list. Nothing is precomputed on the server.

Layout
Spans are grouped under their parent and walked depth-first, siblings sorted by start time. A span whose parent is missing is drawn at the top level.
Scale

Every tool call goes through the gateway. The gateway asks the policy evaluator for a decision, then writes three spans: the call, the policy check as its child, and, if permitted, the twin action as a second child. On a deny, the call span gets status error and no twin span is written. That is exactly what you see in the attack trace: gateway.tool_call cell_sleep in red.

The live INC-2041 trace looks flatter than INC-2040. In the live code every gen_ai.chat, a2a.send and gateway.tool_call span is written without a parent, so they sit at the top level next to incident.handle. Only each gateway call's avp.is_authorized and twin.<tool> spans are indented under it. The pre-warmed INC-2040 nests everything under its root.

Span times are stored rounded to the millisecond. The 0.4 ms policy check therefore often shows as "0 µs" in the live trace, while INC-2040's hand-built one shows "2.0 ms".

Real or simulated

Partly real The ledger records and their signatures are real. The events describe a simulated network and swarm.

Watch out

Ledger numbers differ every run. Read them off the screen. After the beat 12 tamper test, the record at the tampered number fails verification in the Inspector. That is expected.

Questions judges ask about this screen

"Is the cost comparison measured?"
No. It is modelled: simulated token counts times assumed list prices. The frontier column per incident uses a fixed multiplier. Say this before they ask.
"Are these traces in X-Ray?"
Not in this build. Spans use OTel GenAI attribute names and X-Ray id format, and the AWS design sends them through ADOT to X-Ray. No exporter runs here.
"Do the SLOs react to the incident?"
No. They are fixed sample values. The status rules (page at 14.4× over 1 hour, ticket when both windows burn) are live code on those values.
"What would you watch in production?"
Policy deny rate and escalations per agent class (Agent health), p95 per plane (Golden signals), and cost per incident (Cost per incident).
"Does the policy layer slow agents down?"
The policy span is about a millisecond, and Prove p95 sits near 4 ms against a 10 ms objective. Model calls take hundreds of milliseconds to seconds. The timings are simulated, but the check sits on every call.
