Release plane

Release Center

This screen ships a new model version to production safely. A model that passed the Proving Ground is first run in "shadow" (it sees live work but its answers are only compared, never used), then given 10%, 50% and finally 100% of live traffic. Four deployment targets from two vendors are driven from one signed manifest, guard metrics watch every stage, and a bad canary is rolled back automatically, with every step written to the signed ledger.

Route /release Go to it with g then r Appears in demo beats 6

What this screen is for

The one-sentence story: "The model the five operators trained does not go straight into the network. It earns traffic step by step, and if it misbehaves it is pulled back automatically, with a signed record of why."

Release is the third of the five planes (Learn, Verify, Release, Operate, Prove). It sits between the Proving Ground, which decides whether a model is good enough, and the Swarm Tower, where the agents actually use the model. The screen answers three questions a careful network operator would ask before trusting a new model:

  • Where is the new version running, and how much real traffic does it get? (Rollout, Deployment targets)
  • Does it make the same decisions as the version we trust, and when it differs, is it better or worse? (Shadow agreement, Where they disagree)
  • Can we prove exactly what was deployed, and every promotion and rollback? (Version history, Deployment manifest)

The page header carries the track tag T1, which the console defines as "Track 1: NLM training, scaling & production readiness". Release is the production-readiness part of that track.

Where the data comes from (all panels)

Every panel on this screen reads one store slice, release, which mirrors the Release class in backend/spectrum/engines/release.py.

  1. Release enginetick() at 10 Hz, button actions
  2. Eventsrelease.metrics once per sim second, release.stage on every stage change
  3. WebSocket batchevery 100 ms
  4. Store slicerelease
  5. Panels re-renderall eight read the same slice
On connect
GET /api/snapshot returns Release.snapshot(): the state, the full agreement series, disagreements, the last 30 history rows and the static vendor dialect example.
Every sim second
release.metrics carries Release.view(): production and candidate names, stage, per-target numbers, guards, limits, tally, paused flag. While a candidate exists it also carries the last 150 agreement points and the 15 newest disagreements. The store merges it into the slice.
On a stage change
release.stage is emitted with a ledger reference. The store merges the state and adds a history row. The lifecycle ribbon plays a pulse from Release to Operate.
Commands
POST /api/release/advance, /pause, /rollback, /regression, and /shadow (used by the Proving Ground's "Promote to Release" button, not by a button on this screen).

Each panel header ends with a small source chip, for example "SageMaker + Bedrock CMI + ECS" with a flask icon. The flask means "simulated now". Hover the chip: in mock mode the tooltip says what simulates it (for example "Simulated rollout controller") and which AWS service the panel is meant to read in AWS mode. In AWS mode the chip drops the flask and its tooltip says "Live from SageMaker + Bedrock CMI + ECS", but there is no AWS adapter for the release plane in backend/spectrum/adapters/, so the numbers still come from the Python engine. If you demo in AWS mode, do not point at this chip as proof that the rollout is live on AWS.

Store slice

Advance. The engine moves one step along Shadow, Canary 10%, Canary 50%, Full 100%. It sets every target's traffic to that stage's share and its state to "canary" (or "serving" at 100%). It also tells the swarm how many of the 40 site agents should now run the candidate (swarm.cohort event, for example "4 of 40 site agents now run nlm-v7" at 10%). At 100% the candidate becomes production, each target's manifest is regenerated and re-signed for the new version, and the candidate slot empties.

Roll back. Every target goes back to 0% candidate traffic and state "serving", the stage resets, and the regression switch is cleared. All site agents are put back on the production model. The ledger record reads "nlm-v7 rolled back: manual rollback by A. Rivera", and its event has severity warn.

Pause. The server flips a paused flag and returns. Nothing in the engine reads that flag: it does not stop the metrics, does not block Advance, and does not stop automatic rollback. It writes no ledger record and emits no event of its own; the Rollout pill changes to "Paused" when the next release.metrics tick (within about a second) carries the new flag.

Inject regression. The server sets regression = True. On the next once-per-second tick every target with candidate traffic gets +260 ms p95 and +1.6 percentage points of error rate. Error rate jumps from about 0.2% to about 1.8%, which is above the 1% limit, so the same tick rolls the candidate back automatically (see Rollout).

The toasts after each click are written by the browser when the request succeeds. If the request fails, a red toast shows the error message.

How to read it

Greyed-out buttons mean "no candidate in rollout". A bright Advance button with a stage name means a candidate is waiting for a human to promote it.

How to demo it

  1. After beat 6, point at the label "Advance to Canary 50%": promotion is a deliberate human step.
  2. Only if you have time and a judge asks about rollback: say what will happen, then click "Inject regression (demo)".
  3. Watch the Rollout panel return to "No candidate in rollout" and a red row appear in Version history.

What to say

"Promotion is one deliberate click per stage, and every click is a signed ledger record. If I break the canary on purpose, the controller pulls it back by itself within a second."

Judge question it answers

"Who decides when the new model gets more traffic, and can you undo it?" A human advances each stage; rollback is one click or automatic, and both are ledgered. Track T1 (production readiness), Trust (signed records).

Real or simulated

Partly real The stage logic and the signed ledger records are real code; no model is actually deployed, and the metrics the regression changes are simulated.

Watch out

  • Pause only changes the label. Do not claim it freezes the rollout. The key p is different: it pauses the whole simulation.
  • Inject regression rolls back within about a second. Narrate first, then click.
  • If the whole simulation is paused (p), Inject regression and the Paused pill take effect only after you press p again.
  • The paused flag survives rollbacks and promotions. If the pill says "Paused" when a new candidate arrives, click Resume once.
  • To recover after a rollback, press 6 again. The Proving Ground keeps nlm-v7 as its pending candidate, so beat 6 redeploys it in shadow and moves it straight to Canary 10%. The shadow panels restart from zero and Version history gains two new rows.
  • Advancing past 10% puts more site agents on nlm-v7 (20 of 40 at 50%, all 40 at 100%). At 100% nlm-v7 becomes production, Rollout goes back to the empty state and the ribbon reads "nlm-v7 serving", so the later screens no longer match the script. Stay at Canary 10%.

p95 latency means 95% of requests finished faster than this; it captures the slow tail that an average would hide.

How it works

Backend
engines/release.py: STAGES, GUARDS, Release.tick(), advance(), rollback().
Arrives by
Snapshot, then release.metrics (every sim second) and release.stage.
Store slice
release: candidate, prod, stages, stage_index, guards, guard_limits, paused.
Changes when
Gate pass (shadow starts), beat 6 or Advance, Roll back, automatic rollback; meters move every sim second.

Where the guard numbers come from. Once per simulated second the engine gives each target a new p95 and error rate (see Deployment targets). The Error rate and p95 meters show the worst (maximum) value across the targets that carry candidate traffic. In shadow no target carries candidate traffic, so the maximum is taken over all four. Safety incidents is set to 0 when the engine starts and nothing changes it. Shadow agreement is the share of compared decisions that were identical (see Shadow agreement).

The automatic rollback rule, exactly as coded in tick():

  1. Candidate exists
  2. Stage is a canary or laterstage_index >= 1
  3. Error rate > 1.0%worst active target
  4. Roll back"guard breached: error rate 1.8…% > 1%", ledgered, critical event

Only the error-rate guard is enforced. The p95, safety and agreement guards are shown with their limits but no code acts on them. The footnote's "error or latency" overstates this. Because shadow is stage_index 0, nothing rolls back in shadow, which matches the idea that shadow decisions are never used.

States. No candidate (empty state, Stable) → Shadow (gate pass, or beat 6 if no candidate yet) → Canary 10% → Canary 50% → Full 100% (candidate becomes production, panel goes back to the empty state with the new name in the subtitle). From any stage, Roll back returns to the empty state.

Shadow agreement

panel agreement

What it is for

It shows, over time, how often the candidate would have made the same decision as production on the same live incident. This is the main evidence that the new model behaves like the trusted one before it is given real traffic.

How it works

Backend
Release.tick(), same 2-second comparison as card 4.
Arrives by
Snapshot (up to 30 rows), then release.metrics with tally and the 15 newest rows while a candidate exists.
Store slice
release.tally, release.disagreements
Changes when
Every 2 sim seconds while a candidate exists. Reset on the server when a new shadow starts.

When a comparison comes out "different", the engine picks a site at random and writes one of two fixed pairs. Candidate better: production "handover offset +1 dB", candidate "load_balance 2 neighbours", congestion −3 to −11%. Candidate worse: production "wake 1 cell", candidate "handover offset +2 dB", congestion +3 to +11%. The congestion figure is a random number in that range; the twin does not actually replay the decisions. The tally adds one to Identical, Candidate better or Candidate worse for every comparison.

In plain words: a handover offset changes when phones switch to a neighbouring cell; load balancing moves some users to neighbouring cells; waking a cell turns on a sleeping cell to add capacity.

Controls

None. It only displays data. The row list scrolls if it is longer than the panel.

How to read it

Good: a big green number and a small red number, with green winner pills. Concern: red counts rising, or orange "production better" pills piling up.

How to demo it

  1. Clear the spotlight with Esc if it is dimmed.
